CarryForward — App Map

A compact map of what this app is, where the code lives, and how to change it. Snapshot of the latest main (2026-10-27, session 2); the code may drift from this map.

What this is

A local-first project maintainer: open one repository → discover its rules and decisions with file-and-line evidence → approve principles → browse the evidence-linked graph → export a deterministic agent instruction pack → check git diffs against approved rules (findings cite both sides with honest certainty labels) → refresh and resolve stale/conflicting knowledge.

Three pieces: an Express + SQLite server (server/src/), a React UI (web/src/), and shared domain types (shared/types.ts). Everything persists in one local SQLite file under data/ (gitignored). No accounts, no cloud, no AI keys.

One real action, traced

The kernel action: run a change check on a git diff.

A code route (reference — not interactively toured)

Stop 1 — where a scan begins: server/src/routes.ts → the POST /projects/:id/scan handler

Validates the project, runs scanRepository() (from server/src/scanner.ts — the safe, bounded walk), persists files via store.replaceSourceFiles(), then builds knowledge with buildKnowledge() from server/src/graph.ts. This is the only place discovery is triggered.

Stop 2 — where candidates become rules: server/src/approvals.ts → reviewNode()

The single gate for approve/reject/uncertain/deprecate (+optional edits). It writes the new status, stamps local-user attribution, and appends a history row via store.recordHistory(). Scans and refreshes cannot touch nodes marked user_touched.

Stop 3 — where findings get their honesty: server/src/checker.ts → runChecks()

Extracts Forbidden pattern: lines only from user-approved rules, matches added diff lines scoped by path prefix, and labels hits deterministic. The missing-test and status-evidence checks add strong-evidence / needs-human-review findings. Everything the UI shows as a finding originates here.

To change this, start here

  • Add a discovery heuristic → server/src/extractor.ts (parseMarkdown() and the role sets at the top), then mirror the expectation in server/src/extractor.test.ts.
  • Change the pack's wording or sections → server/src/pack.ts (generatePack()); determinism test lives in server/src/pack.test.ts — if you embed time or randomness, it will fail.
  • Adjust graph visuals → web/src/views/GraphView.tsx (the TYPE_COLORS map and the cytoscape style array). Folder drill-down lives there too: double-click a component node renders its stored files as rectangle leaves.
  • Change the standalone report → server/src/report.ts (buildGraphReportHtml()) — one self-contained HTML; the embedded JSON escapes < so it cannot break parsing.
  • Add a maintenance check → server/src/maintenance.ts (detectStale() / detectSupersessionConflicts()); flags need a stable signature so dismissals survive refreshes.
  • Change the database schema → append a new string to MIGRATIONS in server/src/db.ts (never edit an applied migration) and extend server/src/store.ts.

A practice to reuse

Prove the riskiest dependency before building on it. Before any storage code was written, a one-line smoke test opened a better-sqlite3 database in memory and ran a query — the native binary was the one thing that could invalidate the whole plan on Windows. Evidence: the check ran in the first build hour (recorded in doc-of-journey/daily/2026-10-27.md) and the store was only then built against it. The same trick applies to any unfamiliar library: a five-minute probe beats an hour of architecture on top of an assumption.
